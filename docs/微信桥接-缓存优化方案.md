## 一、问题定位（有代码证据）

你的判断是对的：**每一轮请求都会改写前文**，导致 prompt 前缀变化，DeepSeek 的前缀缓存（context cache）几乎无法命中，每轮都按「未命中」计价。

`dsh-social-bridge-plugin` 里有四处「回头改历史」的逻辑：

| # | 位置 | 行为 | 对缓存的影响 |
|---|---|---|---|
| 1 | `native-context.mjs:393` | 每轮开始调用 `migrateChatContext()` + `retireTurnContext()` | 把上一轮的临时资料**替换**成「本轮临时扩展资料已清理。」，改写历史消息 |
| 2 | `native-context.mjs:423-424` | 每轮 `syncInstructionSlot('extensions', …)` 和 `('turn', …)` | 往历史中**插入/替换**指令槽；`turn` 槽内容每轮都变 |
| 3 | `native-context.mjs:437` | 发送前 `dedupePreviousReply()` | 把上一条用户消息里的「上一条已发送的 AI 回复」**原地删除** |
| 4 | `native-context.mjs:605` | 一轮结束后再次 `retireTurnContext()` | 又一次改写历史 |

这四处都用 `surfaceOp: replace`（见 `prompt-context.mjs:77-86` 的 `replace()`），即**在原有位置替换内容**。DeepSeek 的缓存以「前缀完全一致」为命中条件，只要第 N 条消息变了，从它开始往后全部重新计算。

结论：**当前架构下每轮都在重写前缀，缓存命中率接近 0，等同于每轮重开。**

---

## 二、优化目标

| 指标 | 现状（估） | 目标 |
|---|---|---|
| 前缀缓存命中率 | ≈ 0% | ≥ 60% |
| 单轮输入成本 | 全额（未命中价） | 降到 30%~50% |
| 功能影响 | — | 回复质量、@、文件、表情等**不退化** |

> 价格口径：`deepseek-flash` 缓存命中 0.02 元/百万 tokens，未命中 1 元/百万 tokens（**50 倍差**）。因此提升命中率是降本的第一杠杆，优先级高于「少说话」。

---

## 三、总体思路

**把「每轮都变的东西」挪到 prompt 的最末尾；已经写进历史的内容永不回头修改。**

- 历史区（system 头 + 人格 + 已完成对话）：**只追加，不修改**
- 易变区（本轮指令、时间、临时资料）：集中在**最后一条 user 消息**里，且顺序稳定
- 缓存友好：同一会话的第 2 轮起，前面的部分逐字节一致

## 八、方案 A 落地（阈值压缩）

### [x] 步骤 9：启用「阈值触发的一次性压缩」

- 配置位置：`data\workspace\config\wechatagent.json` → `wechat.context`
- 实际值：

  ```json
  "context": { "enabled": true, "maxTokens": 30000, "idleSeconds": 60, "chats": {} }
  ```

- 触发条件（`context-policy.mjs`）：**空闲 ≥ 60 秒** 且历史超过 30000 tokens 时，才做一次摘要压缩。
  对话进行中不会触发，所以不会打断聊天。
- 代价：压缩那一轮前缀被重写 → 该轮缓存未命中；之后重新建立稳定前缀，继续命中。
- 附带修正：原配置里有一条 `"wechat:private:<你的微信ID>": 100000` 的单聊覆盖，
  会把该会话上限顶回 10 万、让 30k 阈值失效，已一并移除。

**事故记录**：改配置时我用正则匹配 `"context": { ... }`，被 `chats` 里嵌套的 `}` 提前截断，
写出了一个非法 JSON。已定位并修复（补回缺失的括号），校验 `JSON=OK`，服务重启后
`adapter ready=True / hook=True / reader=True`、桥接 `ok=True`。

**验收方式**：继续正常聊天，当 `usage-log.jsonl` 的 `totalChars` 增长到阈值附近后，
观察是否出现一次「前缀哈希变化 + 之后重新稳定」，即为压缩生效。
- **实测验证（2026-10-24 12:47，把阈值临时降到 12000 触发一次）**：

  | 指标 | 压缩前 | 压缩后 |
  |---|---|---|
  | 历史节点 `msgs` | 90 | **4** |
  | 总字符 `totalChars` | 183,999 | **17,247**（↓ 91%） |
  | 前缀哈希 `prefixHash` | `0a7f6be8…` | **`5010bc2f…`**（变化一次） |
  | 系统头摘要 `instr` | `ba80439a…` | `ba80439a…`（不变） |

  结论：压缩按预期工作——历史被摘要替换、前缀重写一次、系统头不受影响。
  验证完成后阈值已恢复为 **30000**。
